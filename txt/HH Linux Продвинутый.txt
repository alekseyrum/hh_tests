Вы хотите получить сообщения только текущего сеанса загрузки с уровнем error и выше. Что использовать?

правильный ответ:
++ 		: journalctl -p err -b

ошибки:
-- journalctl --since=today
-- journalctl -b -f
-- journalctl -k -p 3
-- journalctl -u default.target -p error

-b (boot) — указывает journalctl выводить сообщения только текущего сеанса загрузки системы (с момента последнего включения или перезагрузки).
-p err (priority) — фильтрует логи по уровню важности. Значение err (или 3) выводит сообщения с уровнем error и выше (то есть сам error, а также критические crit, alert и emerg)

Скрипт читает список имён файлов из текстового файла filelist.txt, в котором строки могут содержать пробелы. Как безопасно обойти этот список в цикле?

правильный ответ:
++ 		: while IFS= read -r line; do echo "$line"; done < filelist.txt

ошибки:
-- for file in $(cat filelist.txt); do echo "$file"; done
-- while read line; do echo "$line"; done < filelist.txt
-- cat filelist.txt | while read line; do echo $line; done
-- xarg -n 1 echo < filelist.txt

IFS= (Internal Field Separator) — очистка переменной разделителя полей. Без этого read автоматически обрезал бы начальные и конечные пробелы или знаки табуляции в именах файлов.
read -r — флаг -r отключает обработку обратных слэшей (\). Если в имени файла есть символ \, он прочитается как обычный символ, а не как экранирование.
"$line" — кавычки вокруг переменной обязательны. Они защищают имя файла от разделения на отдельные слова при передаче в команду echo или любую другую утилиту.
< filelist.txt — перенаправление ввода напрямую в цикл. Это эффективнее и безопаснее, чем использование конвейера (|).

На сервере с 8 ядрами команда uptime показывает load average: 14.20 15.00 14.80. Как можно интерпретировать эти значения?

правильный ответ:
++ 		: Средняя нагрузка превышает количество доступных ядер - CPU перегружены

ошибки:
-- Значения load average находятся в пределах нормы, загрузка сбалансирована
-- Такая нагрузка характерна для дисковых операций, а не CPU
-- Значения не учитывают многопоточность, нагрузка не превышает порог
-- Низкий load average свидетельствует об ограничении по памяти

*Показатель Load Average (LA) отражает среднее количество процессов, которые находятся в состоянии готовности к выполнению и ждут своей очереди на CPU (а также процессов в непрерывно ожидаемом состоянии, например, из-за дискового ввода-вывода).
Правило идеальной загрузки: Для системы с 8 ядрами значение LA, равное 8.0, означает, что процессор загружен ровно на 100% — все ядра постоянно заняты работой, но очереди из процессов еще нет. 
В данной ситуации: Значения 14.20 15.00 14.80 (за последние 1, 5 и 15 минут соответственно) почти в два раза превышают количество ядер (8). Это означает, что процессор жестко перегружен. В среднем около 6-7 процессов постоянно стоят в очереди и ждут, пока освободится ядро процессора, из-за чего система может ощутимо «тормозить».

Вы настроили таймер на ежедневный запуск сервиса с типом oneshot и добавили в сервис RemainAfterExit=true . Какое поведение будет наблюдаться?

правильный ответ:
++ 		: systemctl будет считать, что сервис активен до следующего вызова, даже после его завершения

ошибки:
-- Сервис будет автоматически перезапускаться при истечении таймера
-- Флаг RemainAfterExit игнорируется при Type=oneshot
-- Таймер будет выполнять сервис только при наличии активного пользователя в системе
-- RemainAfterExit=true приведёт к тому, что таймер не завершится корректно

*RemainAfterExit=true принудительно заставляет systemd считать сервис активным (active (exited)) даже после того, как его основной процесс успешно завершился.
Поведение с таймером: На следующий день, когда сработает ежедневный таймер, он попытается снова запустить этот сервис. Однако, поскольку для systemd сервис всё еще числится «активным», повторного выполнения команд из ExecStart= не произойдет. Таймер просто проигнорирует запуск, так как сервис, с точки зрения системы, уже запущен. (Чтобы ежедневный таймер работал корректно для oneshot-сервиса, параметр RemainAfterExit должен быть равен false, либо вообще отсутствовать).

Конфигурация OpenSSH содержит следующие строки:
PasswordAuthentication no
Match User backup
	PasswordAuthentication yes
Пользователь backup успешно аутентифицируется по паролю. В чем причина?	

правильный ответ:
++ 		: Правило Match User переопределяет глобальные праметры и разрешает парольную аутентификацию только для указанного пользователя

ошибки:
-- Если пользователь задан в Match, глобальные правила игнорируюся полностью
-- sshd не применяет дируективу PasswordAuthentication без AllowUsers
-- Глобальная директива PasswordAuthentication no применяется только для root
-- Match-блоки не поддерживают аутентификацию по паролю без PAM

*Блок Match в конфигурационном файле sshd_config служит для введения условных (специфичных) правил, которые применяются только тогда, когда критерий проверки совпадает (в данном случае, когда подключается пользователь с именем backup).
Настройки, объявленные внутри блока Match, переопределяют (замещают) глобальные директивы, которые были указаны в начале файла.
Таким образом, для всех пользователей в системе вход по паролю полностью запрещен (PasswordAuthentication no), но как только система видит пользователя backup, для него вступает в силу персональное разрешение (PasswordAuthentication yes).

*PAM (Pluggable Authentication Modules) — это системная подсистема в Linux и других Unix-подобных операционных системах, которая отвечает за аутентификацию пользователей.

На сервере с включенным SELinux приложение webapp запущено под собственным доменом webapp_t. В конфигурации SELinux для webapp_t разрешён доступ только к определенным файлам в каталоге /var/www/webapp, а также ограничены сетевые подключения. При этом в системе назначены Linux capabilities CAP_NET_BIND_SERVICE и CAP_DAC_OVERRIDE для бинарника webapp.
При текущей конфигурации существует риск нарушения изоляции и несанкционированного доступа к критическим файлам вне разрешенного каталога.
Что из нижеперечисленного наиболее вероятно объясняет причину уязвимости?

правильный ответ:
++ 		: Назначение CAP_DAC_OVERRIDE позволяет приложению обходить стандартные проверки прав доступа файловой системы, игнорируя ограничения SELinux на уровне DAC, что приводит к возможному доступу к файлам вне /var/www/webapp

ошибки:
-- SELinux ограничивает только доступ к файлам, а capabilities управляют только сетевыми ресурсами, следовательно риск нарушения изоляции исключён
-- SELinux политика по умолчанию игнорирует права capabilities, поэтому назначение CAP_DAC_OVERRIDE не влияет на безопасность
-- Разрешение CAP_NET_BIND_SERVICE позволяет приложению прослушивать сетевые порты ниже 1024, что создает прямую уязвимость в SELinux политике
-- Использование собственного домена webapp_t полностью изолирует приложение, но назначение любых capabilities приводит к отключению SELinux для данного процесса

*SELinux (Security-Enhanced Linux) — это встроенная в ядро Linux система безопасности, которая реализует механизм мандатного управления доступом (MAC — Mandatory Access Control).
*В ядре Linux проверка прав доступа происходит строго по очереди и состоит из двух этапов:
DAC (Discretionary Access Control) — стандартная дискреционная модель прав (владелец, группа, chmod, chown).
MAC (Mandatory Access Control) — мандатная модель (в данном случае SELinux), которая проверяет контексты и политики безопасности.

Вы анализирует запись в /etc/fstab:
/dev/sdb1 /backup ext4 defaults 0 0
Что означает эта запись для проверки файловой системы при загрузке?

правильный ответ:
++ 		: Проверка файловой системы будет отключена

ошибки:
-- Файловая система будет проверяться каждый раз
-- Будет выполнена автоматическая проверка после загрузки

*очередность проверки файловой системы на наличие ошибок утилитой fsck при загрузке операционной системы определяются самым последним (шестым) полем
