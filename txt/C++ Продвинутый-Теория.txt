*Функция в C++20 становится корутиной, если её тело содержит хотя бы одно из ключевых слов: co_await, co_yield или co_return. Они являются "бесстековыми" (stateful) — компилятор преобразует их в конечный автомат, а состояние сохраняет в куче.

Выберите из предложенных вариантов тот, который правильно описывает поведение данного кода:
#include <mutex>
#include <thread>
std::mutex mtx1, mtx2;
void threadFunction() {
    mtx1.lock();
    mtx2.lock();
    std::lock_guard<std::mutex> lock1(mtx1, std:adopt_lock);
    std::lock_guard<std::mutex> lock2(mtx2, std:adopt_lock);
    // Критическая секция
}
int main() {
    std::thread t1(threadFunction);
    std::thread t2(threadFunction);
    t1.join();
    t2.join();
    return 0;
}

++      : Возможен deadlock, потому что мьютексы блокируются по отдельности

ошибки:
-- Корректная работа без deadlock, так как мьютексы захватываются атомарно с помощью std::lock
-- Программа аварийно завершится, так как std::lock не поддерживает несколько мьютексов
-- Ошибка компиляции из-за неправильного использования std::lock_guard
-- Возможно состояние голодания из-за использования нескольких мьютексов

* Для предотвращения взаимных блокировок в C++ следует использовать функцию std::lock(), которая захватывает несколько мьютексов одновременно (атомарно).Чтобы исправить код и обеспечить корректную работу без deadlock, следует переписать threadFunction следующим образом:
void threadFunction() {
    std::lock(mtx1, mtx2); // Атомарный захват обоих мьютексов
    std::lock_guard<std::mutex> lock1(mtx1, std::adopt_lock);
    std::lock_guard<std::mutex> lock2(mtx2, std::adopt_lock);    
    // Работа с защищенными данными
}

Почему один из потоков может выполнить значительно меньше работы?
#include <iostream>
#include <thread>
#include <mutex>
#include <chrono>
std::mutex m;
int shared_data = 0;
void worker(int id) {
    while (shared_data < 100) {
        m.lock();
        if (shared_data < 100) {
            ++shared_data;
            std::cout << "Thread " << id << ": " << shared_data << std::endl;
        }
        m.unlock();
        std::this_thread::sleep_for(std::chrono::milliseconds(10));
    }
}
int main() {
    std::thread t1(worker, 1), t2(worker, 2);
    t1.join(); t2.join();
    return 0;
}

правильный ответ:
++      : Из-за задержки (sleep_for) один поток может чаще находиться в состоянии ожидания, пока другой захватывает мьютекс и выполняет работу

ошибки:
-- Потому что мьютекс неблокирует один поток, если второй поток успел его захватить первым
-- Потому что переменная shared_data не объявлена как atomic, и один поток может не видеть изменения другого
-- Потому что планировщик операционной системы всегда отдает предпочтение одному потоку
-- Потому что мьютекс блокирует один поток навсегда, если второй поток успел его захватить первым

*В данном коде задержка std::this_thread::sleep_for вынесена за пределы критической секции (после m.unlock()). На практике системные часы и планировщик ОС работают несинхронно. Если один поток просыпается чуть раньше или планировщик выделяет ему более длинный квант времени, этот поток может успеть:Проснуться.Проверить условие цикла.Захватить мьютекс, увеличить переменную и отпустить мьютекс.Снова уйти в сон.В это время второй поток может всё ещё спать или только просыпаться. Из-за такой микроскопической рассинхронизации один поток начинает постоянно «опережать» другой, из-за чего он успевает сделать гораздо больше итераций, пока второй поток находится в состоянии сна или ожидания своей очереди. Это классическое проявление недетерминированного поведения планировщика потоков ОС.
